# GPU Adaptation Methodology

**skill 是可传导的能力**：一个没有先验知识的 agent 拿着它，应当能在任何 GPU 平台上
系统性地把"某语言/工具链的能力"推进到"该硬件真正支持的边界"，并且每一步都有
可审计的证据。本文不假设任何特定编译模型——遇到本文没有的平台机制时，用
第 1 节的调查框架去建立理解，而不是套用其他平台的类比。

## 0. 证据纪律（贯穿全程的元规则）

每条知识必须带证据等级标记，写进任何文档/汇报时保持标记：

| 等级 | 含义 | 可声明的上限 |
|---|---|---|
| verified-on-hardware | 真机执行 + 独立正确性校验（输出对独立参考，不是自比自） | SUPPORTED |
| probe | 探针/负探针实验（汇编器拒绝、编译器拒绝、真机 flag 实验等） | 能力边界成立 |
| measured | 真机测量数据（带方法：计时方式、次数、状态控制） | 性能事实 |
| inferred | 从机制推理，未实测 | 假设（须写明验证途径） |
| historical | 旧版本/旧环境记录，未在当前环境复验 | 仅作线索 |

三条红线：
- 编译通过 ≠ 链接成功 ≠ kernel 启动 ≠ 计算正确。四件事分开报告。
- 不隐藏失败实验——失败的假设比猜测值钱（它排除了一个方向）。
- 推断可以自由形成，但包装成事实之前必须有 probe 或 e2e。

## 1. 边界调查：先建立"三层存在性"地图

适配的每个能力项，先回答四个存在性问题，再动手：

1. **硬件有没有？** 找 ISA 手册级证据。拿不到手册就做汇编器/编译器负探针：
   让汇编器汇编目标指令，拒绝输出就是硬件/后端缺口的直接证据
   （例：`llvm-mc -show-encoding` 对目标指令报 "instruction not supported"）。
   注意区分"硬件没有"与"后端没实现"——同一份拒绝输出，两者都可能，
   需要第二证据（官方 spec、同代指令集对照、上游 gate 条件）。
2. **底层软件有没有？** 编译器/后端/Runtime 的源码级考古：搜指令选择、
   intrinsic lowering、Runtime API 的 gate 条件。上游常按架构代号门控——
   找到 gate 就找到了"为什么没有"的准确答案。
3. **语言工具链有没有？** 语言前端/绑定层是否暴露。没有暴露点不等于
   不可用——记录"缺的是哪一层"。
4. **当前环境能不能验证？** 不能真机验证就推进离线路径（交叉编译、
   IR 级分析、参考实现），但结果必须标记为未验证，不得冒充实机通过。

每项归入分类：SUPPORTED / IMPLEMENTABLE（理论可行未实现）/ BLOCKED（外部依赖，
附阻塞点）/ HARDWARE_LIMITED（附探针证据）/ NOT FEASIBLE / OUT_OF_SCOPE（附理由）。
不得因为实现困难而归入排除类。

## 2. 上游考古：读源码，不读宣传

- 从最终现象倒查：一个功能"不工作"，沿 调用栈 → Runtime API → 编译器 lowering
  → 目标 IR → 硬件指令 的顺序找第一个"没有"的环节——那才是适配的真正入口。
- 上游的处理方式是最便宜的方案来源：搜同项目对其他架构的分支/特化
  （例：某 kernel 在架构 A 走专用指令、在架构 B 退化为通用路径——那条退化
  路径往往就是你的替代实现雏形）。
- 版本差异是常态：同一 API 的 ABI 语义、默认值、校验严格度会跨版本变化。
  升级适配时先跑一遍旧验证集再下结论，不得假设旧行为延续。

## 3. 缺口因果定位：区分五类根因

功能缺失时，根因只有五类，处理方式完全不同：

| 根因 | 识别特征 | 处理 |
|---|---|---|
| 硬件缺失 | 负探针拒绝 + spec 无此指令 | HARDWARE_LIMITED；转替代实现研究 |
| 后端未实现 | spec 有、编译器 gate 没有 | IMPLEMENTABLE；自实现或等上游 |
| 前端/绑定未实现 | 后端有、语言层没暴露 | IMPLEMENTABLE；补绑定 |
| 环境缺失 | 依赖/权限/版本不满足 | BLOCKED；列精确前置条件 |
| 语义依赖宿主特性 | 依赖统一内存/驱动特性能 | 评估语义等价的替代 |

不要把"上游某个 kernel 不支持本架构"放大为"整个功能不可能"。
不要把"当前实现没有"误判为"理论不可能"。

## 4. 替代实现策略（六分类）

每条替代必须声明类别、语义、正确性条件、适用范围、资源成本：

1. **NATIVE** —— 目标硬件原生有等价物：查 ISA 对照表，直接映射。
2. **INSTRUCTION COMPOSITION** —— 用现有指令组合出相同语义
   （成本=指令密度；实测指令密度损失常为 4-7×，勿按乐观估计报性能）。
3. **ALGORITHM SUBSTITUTION** —— 换算法达到相同功能
   （正确性条件要重列，成本=复杂度/精度差异）。
4. **SOFTWARE EMULATION** —— 软件模拟缺失的操作/语义
   （协议级模拟可行，但要确认性能可接受）。
5. **ALTERNATIVE BACKEND** —— 换执行通道（如设备格式化走宿主服务协议）。
6. **NOT FEASIBLE** —— 已验证的技术障碍（必须附证据，且注明"在哪些前提下
   重新开放"，例如"下一代硬件出现后同基准复跑"）。

功能可行性与性能可行性分开报告：软件替代功能可用 ≠ 性能可用。
性能验收用**梯度制**（相对参照路径）：60% 及格 / 70% 良好 / 80% 优秀 /
90% 完美替代 / 超硬件理论值 = 需要复核测量方法（多半是测到了缓存或
异步完成语义的假象）。

## 5. 验证设计：最小复现 + 独立正确性 + 性能三件套

- **最小复现**：每个能力点一个最小用例。用例必须让"实际执行的设备与路径"
  可观察——在输出里带设备侧证据（设备名、路径标记），否则无法区分真机
  与 fallback。
- **独立正确性**：输出对独立参考校验（host 计算的期望值、数学恒等式、
  位模式），禁止"自己跑两遍对一遍"。
- **性能测量**：先控状态再计时——设备时钟有 DVFS，冷态与暖态差 5-10%；
  预热协议固定下来再测；计时前后的隐式异步完成（posted write）会把
  带宽测高 30-40%，必须核实"完成信号 ≠ 数据落盘"。所有性能数字记录
  测量协议，否则不可比。
- 失败测试保留不删。回归集是适配的资产。

## 6. 中间表示契约：合成构造必须走"被认可的路"

有验证器的中间表示（任何主流编译器都有）对每个操作有类型/地址空间/来源
授权的精确契约。为绕过缺口手工合成构造（伪造指针、伪造全局、伪造转换链）
时，会连续撞上多层验证器，每一层只放行一种"被认可的路"。
经验法则：**撞两次验证器墙后，停止逐个绕，去找"上游合法产生这种构造"的
机制**（前端是怎么合法生成它的？照那个机制造）。把每堵墙的精确报错记录
下来——它们定义了缺失基础设施的准确形状，是子工程的工作量依据。

## 7. 环境易变性与可复现

- 适配环境常在活跃退化（工具链目录被清、凭证失效、网络代理变更）。
  先探测再使用（`which`/存在性检查），持久资产放稳定位置并推远端。
- 完整环境要能从零重建：把重建步骤固化成幂等脚本，并把"容器镜像/锁文件/
  工具链 pin"纳入交付。宿主保持最小依赖，重资产放容器，是降低环境脆弱性的
  有效形态。
- 跨栈零漂移验证：同一基准脚本在不同重建栈上跑，数字吻合才能证明
  历史数据在新栈仍然有效。

## 8. 知识沉淀与回写

- 每次适配结束，按"换什么才失效"分层回写：换软件栈才失效 → 平台层；
  换硬件架构才失效 → 架构层；换语言/工具链才失效 → 工具链层；换平台/架构
  都还成立 → 方法论层（提炼时必须论证跨平台性，举出至少两个平台成立的理由）。
- 推翻历史结论时保留旧记录（标注 superseded + 原因），不删除。
- 新版本适配先复用已验证路径，但必须重新确认前置条件——旧版本不支持
  不默认新版本也不支持，反之亦然。

## 坑表（每条都有真实事故背书）

- **"跑通了"可能是 fallback**：设备代码在 CPU 上静默回退仍会打印成功。
  验证输出必须带设备侧指纹。
- **格式化输出串行化**：设备端格式化（printf 类）走宿主服务协议时是同步
  往返，放进热路径会杀死性能——只用于调试面。
- **参数槽数 < 签名形参数 → 崩在 Runtime 内部**：kernel 元数据遍历越界类
  崩溃先查"每个形参都有槽位吗"，再看对齐空洞（打包结构体的 padding
  不是参数槽）。
- **链式协议有上限**：服务协议按固定槽数分轮时，返回句柄必须接力到下一轮，
  is_last 只在末轮置位——漏接力表现为输出错位/截断。
- **性能假象三件套**：缓存驻留（工作集 < 缓存容量时数字虚高数倍）、
  posted-write 完成语义（完成 ≠ 落盘）、DVFS 冷态（首测偏低 5-10%）。
  出现"超过理论值"先怀疑测量，再怀疑世界。
- **CPU 侧语义修好后设备侧仍错**：对照实验锁半场——用另一工具链编译
  同形态代码在同一硬件上跑，工作则问题在本工具链管线，不在硬件/宿主。
- **验证器报错的字面意思常常不是根因**：类型不匹配报错下面往往是
  "这个构造本来就没有合法的产生方式"。把报错当线索，不当结论。
